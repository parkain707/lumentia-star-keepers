# Teacher reward ledger

The game and `/teacher` remain static Vercel pages. `server/index.ts` and `gateway.js` are deployed as the dedicated Supabase Edge Function `lumentia-rewards`. These backend sources and SQL files are excluded from the static deployment by `.vercelignore`.

Only the isolated `lumentia_private` schema and `public.lumentia_gateway` RPC are added to the approved shared project. Existing schemas, Edge Functions, Supabase Auth, and API exposure settings are unchanged. Apply `schema.sql` and `prior-payments.sql` together on a fresh database before serving traffic. The canonical gateway in schema.sql calls allocate_prior from prior-payments.sql. No production credentials, setup keys, or real student names belong in source control.

All tables enable RLS with default denial. `anon` and `authenticated` have no schema, table, or RPC access. The RPC and private functions are SECURITY INVOKER and executable by the backend service role only. The Edge Function authenticates student secrets or teacher sessions through the private gateway; platform JWT verification is disabled for this custom authentication flow. Backend keys come from managed function environment variables and are never returned to clients.

The teacher email is configured server-side. A cryptographically random one-time setup key is delivered privately; only its SHA-256 digest is stored. The owner sets a 12+ character password in the UI; bcrypt cost 12 protects it. The setup key is discarded after use. Opaque teacher sessions expire in 8 hours and are revoked on logout; only their hashes are stored. Login attempts are rate limited. Teacher session tokens remain in sessionStorage, never URL parameters. Recover a lost teacher password through the authenticated database owner: revoke teacher sessions and issue a fresh one-time setup key. Do not put recovery keys into the repository.

Each existing local student account receives a random reward identity and secret. Transfer codes preserve that identity, so transferring an old game save cannot erase server payments. The secret must remain private; transfer codes grant access to the player's reward identity as well as the game save. Hero and growth saves stay local. The reward API validates the daily two-record/20,000 limit and immutable settlement amounts, but it is not a server-authoritative gameplay simulation. Teachers must compare the student number and settlement number with ClassTalk before payment.

`requested_at` is a student assertion. Only teacher-confirmed `received_at` preserves unpaid awards beyond the 72-hour submission window. A teacher can later confirm a historical receipt that actually arrived before expiry. Payments require verified receipt, positive integer amounts, row locks, expected revisions and an idempotency request UUID. They preserve original earned amounts and append immutable audit rows.

Teacher-verified prior payments are stored separately from earned awards. They offset only their specified reward day, once, up to the exact amount actually paid. Unallocated credit stays visible until the student's awards arrive. Unique exact names auto-link; other nicknames require teacher linking by student number. Original payment times are retained. The allocation trail records which claim received each offset; daily earned totals and growth wallets never change. Personal names and source receipt details are stored only in the private database.

Verification: `npm test` runs the existing game regression tests plus gateway and student reconciliation tests. `tests/ledger.sql` and `tests/prior-payments.sql` run synthetic database assertions inside transactions and roll back all fixtures. The local development server has an isolated mock ledger for UI review; it never reaches the production reward API.
